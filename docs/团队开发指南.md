# 团队开发指南 · 从一句需求到合并上线

> 给全体组员的入口文档。你不需要懂全部代码——只需要：想清楚要什么 → 用对提示词让 AI 改 → 按清单自测 → 提 PR。
> 红线与命令速查见 [AGENTS.md](../AGENTS.md)；产品边界见 [product-requirements.md](product-requirements.md)；本文管"怎么干活"。

## 一、先认角色，再看对应章节

| 你的角色 | 你要做的 | 只看这几份 |
|---|---|---|
| 产品/运营（只改数据） | 改 CSV / 营销案例 | README「更新数据」一节 + [marketing-data-guide.md](marketing-data-guide.md) |
| 提需求的人 | 描述现象与期望 | 本文档第四节 + [interaction-backlog.md](interaction-backlog.md) |
| 开发（含 AI 协作） | 改代码走完全回路 | 本文档第二、三节 + AGENTS.md |
| owner | 部署 | [deployment.md](deployment.md) + [deploy-cutover.md](deploy-cutover.md) + [release-checklist.md](release-checklist.md) |

## 二、开发回路（七步）

1. **领需求**：从 [interaction-backlog.md](interaction-backlog.md) 认领一条，或自己发现新问题先补录一条；
2. **建规格（Spec Kit，SDD）**：在仓库根目录 PowerShell 运行
   `.specify/scripts/powershell/create-new-feature.ps1 简短功能名`
   生成 `specs/00X-xxx/`（spec/plan/tasks 三件套）。先填 **spec.md**（要什么、验收标准），不确定的留给 clarify 阶段问；已批准的规格示例看 `specs/004-unified-workbench/spec.md`；
3. **起本地环境**（无需 Docker/数据库，约 2 分钟）：见 README「快速开始」；
4. **让 AI 改**：把 spec + 本文档第三节的提示词卡丢给 AI（仓库里的 AGENTS.md 会自动约束它）；
5. **自测**：按 spec 的验收标准手动过一遍 + 跑测试（命令在 AGENTS.md，注意后端测试**按模块逐个跑**）；
6. **提 PR**：功能分支 → PR（模板自动出现，填自测清单）；涉及交互改动**必须附截图**；
7. **等 CI 与 review**：CI 自动跑 113+12 项测试和密钥门禁；合并进 main 后生效，部署由 owner 按手册执行。

## 三、提示词卡（按改动类型直接复制，替换 ⟨⟩ 内容）

**卡 1 · 改交互逻辑**（最常见：行为/流程/状态不对）
```text
请先读 AGENTS.md 和 specs/004-unified-workbench/spec.md。
需求：⟨现象：现在是什么行为⟩；期望：⟨应该是什么行为⟩；复现：⟨步骤⟩。
先定位相关代码（前端在 frontend/src/，后端在 backend/app/marketing_agent/），
说明你的理解和改动方案，经我确认后再改。只改与需求直接相关的文件，
不改动无关行为；完成后告诉我如何自测。
```

**卡 2 · 改业务规则**（口径/限制/校验）
```text
请先读 AGENTS.md、docs/product-requirements.md 第 4 节（经营判断统一口径）
和 .specify/memory/constitution.md。
需求：⟨规则现状⟩ 应改为 ⟨新规则⟩，原因是 ⟨业务依据⟩。
评估该规则影响哪些路径（提示：策略门槛在 graph.py，固定条款在 content.py，
确定性计算在 business.py）。规则变更需要同时更新对应测试的断言。
```

**卡 3 · 加字段/数据**
```text
请先读 AGENTS.md 和 docs/marketing-data-guide.md。
需求：给 ⟨品牌/商品/活动⟩ 增加 ⟨字段⟩，来源是 ⟨用户填写/文件解析/计算⟩，
必填性与默认值：⟨…⟩。注意源文件进 Git、数据库是生成物；
后端涉及 contracts.py 与 store.py 的表结构，前端涉及对应管理页。
```

**卡 4 · 修 Bug**
```text
请先读 AGENTS.md。Bug：⟨现象⟩；复现：⟨步骤⟩；期望：⟨正确行为⟩。
先复现或解释根因，给出最小修复方案；禁止顺手重构无关代码。
如果根因在测试覆盖不到的地方，补一条能防回归的测试。
```

## 四、业务逻辑速查地图（哪类需求动哪里）

**核心链路一句话**：对话补问收资料（intake）→ 用户确认成事实（facts→knowledge，PG）→ 需要案例参考时检索 RAG（retrieval→rag.py，SQLite）→ 策略与测算走确定性计算（business，**模型不算数**）→ 文案生成（content，白名单上下文）→ 图片（materials）→ 全程按任务持久化（store）。

| 改动类型 | 主要位置 |
|---|---|
| 对话流程/补问逻辑 | `backend/app/marketing_agent/intake.py`、`questions.py`、`graph.py`；前端 `frontend/src/agent.js` |
| 品牌事实/确认机制 | `facts.py`、`knowledge.py`、`knowledge_index.py` |
| 检索质量/案例库 | `retrieval.py` + `backend/app/rag.py`；数据在 `marketing/` |
| 经营测算/优惠校验 | `business.py`（确定性计算）、`graph.py`（策略门槛） |
| 文案规则/固定条款 | `content.py` |
| 页面布局/导航/状态 | `frontend/src/workbench.js`、`router.js`、`agent-workspace.js` 及对应 css |
| 任务状态/历史/恢复 | `store.py`、`runtime.py`、`archive.py` |

**三条业务铁律**（改任何东西都不许破坏，完整版见 constitution）：
1. 商品事实必须来自用户**确认**的资料，营销案例只作写法参考、不是事实依据；
2. 经营数字由**结构化工具计算**，模型只负责表达，"未知"不得当零处理；
3. 涉及交易条件的文案必须绑定**已批准、未失效**的策略。

## 五、交互问题清单（interaction-backlog）

发现交互/逻辑问题 → 先在 [interaction-backlog.md](interaction-backlog.md) 按模板补一条（现象/期望/复现/建议模块/优先级），再按第二节回路认领开发。**新功能建议同样先录一条再讨论**，避免口头需求丢失。每条解决后在 PR 合并时勾销。
