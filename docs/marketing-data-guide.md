# 从品牌上传到营销文案：数据准备与验收指南

更新：2026-11-18。按当前本地代码能力编写。对象：PM、品牌资料组、经营分析组、Agent/前后端组。

## 1. 先准备什么

第一轮只做 **一个品牌、一个门店、2–3 款商品、两段可比较的销量区间、三种已有优惠方式**。先完整跑通，再扩大规模。若没有获准使用的真实经营数据，用本目录的虚构品牌案例，明确标为测试数据。

不要求用户一次填完所有资料：建品牌、普通文案、单位优惠检查、活动策略各有自己的数据门槛。Agent 只追问当前任务必需的缺项，互相独立的问题一批最多三项。

| 数据包 | 至少准备什么 | 谁负责 | 什么时候必须有 |
|---|---|---|---|
| 品牌事实 | 品牌名称、介绍；建议定位、主要受众、表达风格、禁用词 | PM / 品牌资料组 | 建品牌时名称、介绍必需 |
| 商品事实 | 商品名称、可核实卖点；建议规格、分类；测算前须明确售价 | 品牌资料组 | 商品创作前；同名多规格必须补规格 |
| 资料证据 | 文件原件、资料日期/适用范围、出处；图片的商品对应关系与使用授权 | 品牌资料组 | 入库与审核时 |
| 经营事实 | 商品 ID、两期起止日期、净完成杯数、单杯变动成本 | 经营分析组 | 销量对比和活动 ROI；单位优惠可只补成本 |
| 经营约束 | 最低单杯贡献要求、可选日容量 | 店主 / 经营分析组 | 声称优惠“满足门店约束”之前 |
| 活动需求与假设 | 目标、平台、商品、活动期、受众、主题、预算上限、预计额外支出、销量情景、优惠方式及参与量 | PM / 用户 | 策略与情景测算时 |
| 写作参考 | 平台、行业、文案、写作结构、来源；建议 10–20 条经过筛选的案例 | 文案 / RAG 组 | 提升表达质量；不是交易事实依据 |
| 验收样例 | 输入文件/补充对话、应问问题、正确计算值、必须拒绝的情况、期待修改范围 | 各组共同维护 | 每次迭代验证 |

来源、有效期、渠道适用范围等应先记录在资料清单中；当前数据库并未将它们全部建成独立字段。不要把“建议收集”理解成“当前已经全部自动解析”。

## 2. 上传解析和入库怎么走

1. 新对话说明“为我的品牌建档”，上传品牌/商品文档。Agent 当前接收 TXT、MD、CSV、文字型 PDF、DOCX；扫描 PDF、任意 Excel 和图片 OCR 不属于这条上传链路的保证能力。
2. 提取原文，整理品牌与商品草稿。图片可在产品库关联上传；图片本身不能替代商品价格、规格和卖点证据。图片/视频生成闭环仍后置。
3. 检查当前任务必填项、同名商品规格、已有资料冲突。未知保持空；有冲突先展示新旧差异。文件内的指令不能改变 Agent 的规则。
4. 一批询问独立的缺项，用户可选项作答或自由补充。补充写回当前草稿，无须重传整份文件。
5. 用户核对并明确确认后，资料成为有效品牌事实。草稿不能提前显示成“已知品牌”；原件、版本、来源和确认事件保留。
6. 后续任务检索该品牌的有效资料；经营成本与销量走结构化工具计算。营销案例只帮助风格和结构，不能把别人的商品事实带进当前品牌。

当前只处理一份待确认附件；先确认/放弃，再传下一份。品牌知识入库与经营数据确认是两个独立步骤。

## 3. 经营表字段：严格沿用当前模板

在已有品牌的对话中点 **添加资料 → 经营汇总 CSV → 下载当前品牌模板**。模板带真实 `product_id`。不要手填商品名充当 ID，也不要把仓库模拟门店的 T001 混进自己的品牌。

| 字段 | 格式与例子 | 口径 |
|---|---|---|
| product_id | 模板生成的商品 ID | 对应已确认、未归档商品；一款一行 |
| current_start / current_end | 2026-11-02 / 2026-11-16 | 本期 14 天，包含开始、不含结束 |
| previous_start / previous_end | 2026-10-19 / 2026-11-02 | 上期等长、不重叠；所有商品区间相同 |
| current_qty / previous_qty | 140 / 200 | 净完成杯数；去掉取消、退款，不是订单数 |
| variable_cost_minor | 650 | 每杯食材、包材等变动成本，整数分 = 6.50 元 |
| min_contribution_minor | 500 | 每杯最低贡献收益，整数分 = 5 元；不是毛利率 |
| daily_capacity | 200 | 所选商品可履约的日容量；可空，但将无法验证容量约束 |

文件为 UTF-8 CSV，表头不能随意增加；不要上传金额单位为元的数值到 `*_minor`。没有信息就留空，不能用 0 代替未知。只想核对优惠、不做 ROI 时，可在对话中补成本，无需经营表。

**当前上传确认会替换该品牌上一批经营汇总，不是逐行追加。** 更新时保留本次需要的所有商品行，先核对再确认。原始 POS 明细、固定房租工资、退款金额、渠道分成和多门店汇总并未由这份表完整表达。

当前适用的是单门店自提。小红书/抖音/公众号是内容投放平台；它们不是销售渠道费的代称。外卖佣金、平台补贴与商家承担比例未纳入该测算器。

## 4. 活动输入与营销手段

活动参数写入本次任务，不能覆盖长期品牌事实：`platform`、`goal`、`audience`、`theme`、`constraints`、`start_date/end_date`、`budget_minor`、`spend_minor`、`scenario_qty`、`offer`、必要时 `promotion_pairs`。系统用 JSON 校验和保存，普通用户用自然语言补充即可。

预算是上限，`spend_minor` 是额外营销支出假设；促销让利已经体现在收入里，不能再加一次。`scenario_qty` 是用户确认的情景，不是 Agent 承诺的销量。新商品没有历史基线时，先做单位收益，不编造 ROI。

| 营销手段 | 当前支持程度 | 额外需要的数据 |
|---|---|---|
| 品牌/商品介绍、节令主题文案 | 支持普通文案 | 品牌/商品事实、平台，建议目标、受众、风格；不用成本与 ROI |
| 原价活动 | 支持 `offer.type=none` | 明确原价；ROI 另需基线、日期、销量与额外支出假设 |
| 每杯统一折扣 | 支持 `percentage` | 支付原价比例；如九折为 `pay_bps=9000` |
| 同款第二杯优惠 | 支持 `second_cup_discount` | 同单同款两杯重复配对、不叠加；活动需指定参与组数，每组仅一杯折价 |
| 满减、优惠券 | 后置，不能输出“已校验可行” | 订单购物篮、门槛、券面额、领取/核销、叠加、成本承担方 |
| 组合套餐、买赠 | 后置 | 每款数量/成本、组合价、赠品成本、参与组合量、退款规则 |
| 会员积分、复购激励 | 后置 | 授权使用的客户/复购队列、权益成本、核销周期、历史对照；不需要姓名电话 |
| 自动发文、海报视频闭环 | 后置 | 账号授权、素材版权、图片/视频规格、审核流程及服务接口 |

“节日活动”是主题，不自动定义交易机制。若用户要求“立冬促销”，仍需澄清是否折扣、第二杯优惠或只做内容传播。当前不做 CTR/CVR，也不将销量下降自动解释为某个原因。

## 5. 可复现案例：山茶小站（完全虚构）

样例在 [examples/marketing-case](examples/marketing-case/)。建议使用独立测试品牌，避免污染真实品牌。

**A. 验证补问与品牌入库**

- 上传 `01-brand-incomplete.txt`，它只包含品牌名、商品名和规格。
- 应同时询问品牌介绍与商品卖点，不应该先索要销售量/成本/ROI。
- 回复：`品牌介绍：服务校园学生的茶饮小店；可核实的商品卖点：桂花香气与鲜奶搭配。`
- 核对并确认；右栏显示已确认品牌，产品库出现桂花鲜奶茶 500ml。此时售价仍未知，但可说 `帮我写一篇小红书商品介绍，不做优惠活动`。
- `02-brand-complete.txt` 是另一种完整上传路径；已有商品时上传会展示差异，尤其价格需核对。案例设价 18 元，仅为合成测试值。

**B. 验证经营事实**

- 确认商品售价 18 元；下载当前品牌模板。
- 按 `03-business-values.json` 填写对应商品行。该 JSON 是填写参考，**不直接作为 CSV 上传**。
- 两期 200 → 140 杯，本期日均 10 杯，变化 -30%。这只能描述变化，不能证明营销失败或产品滞销原因。
- 将 CSV 上传、核对并确认。缺少成本时应补问；不要先填假成本让流程通过。

**C. 验证策略与批准**

发送：`想做周末促销。推广桂花鲜奶茶500ml，发小红书，面向校园学生。活动是2026年11月21日到22日，共两天；预算上限200元，预计额外宣传支出100元；假设卖40杯，其中10组同单两杯参加第二杯半价，其余单杯原价；不叠加其他优惠、仅门店自提。请根据已上传销量和成本判断，再给我策略确认。`

系统日期应存为 `[2026-11-21, 2026-11-23)`。检查事实、假设和优惠方式，**明确点击批准当前策略版本后才生成带优惠承诺的文案**。模型可能先追问活动目标或要求核对条件，正常回答即可。

| 检查项 | 正确值 |
|---|---|
| 参与优惠两杯售价 | 18 + 9 = 27 元 |
| 参与组平均每杯贡献 | (27 − 2×6.5) ÷ 2 = 7 元 ≥ 最低 5 元 |
| 情景收入 | 30 杯原价 + 10 杯半价 = 630 元 |
| 情景销售贡献 | 630 − 40×6.5 = 370 元 |
| 不促销比较基线 | 本期日均 10 杯×2 天×(18−6.5) = 230 元 |
| 扣除支出后的增量贡献 | 370 − 230 − 100 = 40 元 |
| 情景增量 ROI | 40 ÷ 100 = 40% |

7 元是“参与优惠两杯”的平均贡献，不是全部活动杯数的平均贡献；全部 40 杯销售贡献均值是 9.25 元。它们都不是扣除房租、固定工资后的净利润。

**D. 验证调整与风险**

- `只改标题，活泼一点，优惠和日期不变`：正文和交易条件不应被偷偷重写，产生可回溯新版本。
- `改成第二杯七折`：重新测算、产生新策略版本、再次确认，不能沿用旧批准。
- 假设销量改为 20 杯、参与 10 组：单位仍为 7 元，但活动增量贡献是 -190 元，ROI -190%；必须展示亏损风险。
- 单杯成本改为 10 元：第二杯半价的平均贡献只剩 3.5 元，不满足最低 5 元，不得批准为可行优惠。
- 支出填 0：展示增量金额，ROI 不输出无穷大。
- 不知道参与组数/销量/基线：补问，或退回只看单位收益，不自动配对、不补造销量。

`04-scenarios.json` 保存可重复校验值。九折、原价情景使用同样的 40 杯量，只是收益敏感性对比，**不能据此宣称原价最优**；真实需求会随价格改变，目前没有需求预测模型。

## 6. 如何安排数据工作

1. 品牌组交付：1 份品牌介绍、2–3 款商品资料及授权图片、出处/有效期清单；另准备缺项、同名多规格、矛盾价格三类坏样例。
2. 经营组交付：带正确 ID 的经营 CSV、字段说明、三种优惠的人工计算答案；真实数据与合成数据分开。销量按同一渠道/门店/口径整理，先处理重复、取消和退款。
3. PM 确认：四条任务的范围；最低贡献标准；活动允许的优惠；哪些动作须用户批准；哪些建议只能标成假设。
4. Agent/工程组交付：解析→草稿→补问→确认的追踪记录，工具 JSON 校验，策略版本和批准记录；默认不让成本、模型密钥等进入公开文案。
5. 全组维护 15–20 条验收案例：完整/缺项/冲突/重复规格、品牌串库、单位收益与负 ROI、零支出、错误日期、改策略失效、只改标题、刷新恢复、作品回溯。记录实际结果，不只做截图。

现阶段不必采集姓名、手机号、聊天私信或完整顾客画像。RAG 不应承担金额计算；经营数据不是一股脑放进向量库。长期品牌事实、结构化经营数据、当前任务假设、原始附件和生成作品分别保存并通过 ID/版本关联。

## 7. 当前保存位置与后续扩展

本地启动器默认把业务数据库放在 `.local-data/agent/brand-knowledge.db`，原件在 `.local-data/agent/brand-files/`；会话、品牌、作品和经营汇总使用业务数据库，LangGraph checkpoint 另存于该运行目录。其他 `--runtime` 是独立数据环境。

营销案例 RAG 有自己的索引/重建流程，品牌事实检索在品牌知识库。模型不是长期记忆载体。前端未发草稿保存在当前浏览器会话，已提交消息与执行状态由后端持久化。

要增加满减、券或套餐，先补定义和数据契约、计算样例、失败边界，再增加工具和 Agent 可用能力。不能只加提示词就宣布支持新的优惠计算。
